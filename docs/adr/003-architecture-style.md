# ADR-003: Выбор архитектурного стиля

| Поле | Значение |
|---|---|
| Статус | Accepted |
| Дата | 2026-09-30 |
| Автор | Тетюшкин Н.Д. |

## Контекст

ExpenseBot — небольшое приложение с понятной предметной областью: разбор сообщения, сохранение расхода, построение отчёта. Над проектом работает один разработчик, срок — 8 недель. Приложение запускается одним процессом на одном VPS.

Ключевые требования к архитектуре:

- Бизнес-логику (разбор текста, подсчёт отчётов) нужно тестировать без Telegram и без реальной базы данных.
- Слой хранения должен заменяться (SQLite → PostgreSQL), как описано в ADR-002.
- Код должен быть понятен проверяющим и другим студентам: простая структура важнее гибкости «на вырост».
- Должны выполняться нефункциональные требования PRD: сопровождаемость, тестируемость, покрытие не менее 70%.

## Рассмотренные альтернативы

1. **Монолит без слоёв** — вся логика в обработчиках Telegram.
2. **Слоистая архитектура (layered)** — обработчики → сервисы → репозитории.
3. **Гексагональная архитектура (порты и адаптеры)** — ядро, окружённое портами и адаптерами.
4. **Микросервисы** — отдельные сервисы для бота, хранения и отчётов.
5. **Событийная архитектура** — компоненты общаются через очередь событий.

## Решение

**Слоистая архитектура** в виде одного развёртываемого модуля (модульный монолит) с тремя слоями:

- **Handlers** — приём сообщений Telegram и формирование ответов;
- **Services** — бизнес-логика (`ExpenseService`), парсер сообщений;
- **Repositories** — доступ к данным (`ExpenseRepository`).

Зависимости направлены только сверху вниз: обработчики знают о сервисах, сервисы — о репозиториях, но не наоборот.

## Обоснование

- Слоистая архитектура проста и хорошо знакома; для приложения с тремя сценариями она достаточна и не создаёт лишних абстракций.
- Разделение слоёв позволяет тестировать сервисы без Telegram: достаточно создать репозиторий с базой `:memory:` (см. doctest в `ExpenseService`).
- Изоляция доступа к данным в репозитории выполняет требование ADR-002 о будущей замене базы.
- Гексагональная архитектура даёт ещё более строгую изоляцию, но требует интерфейсов (портов) для каждой внешней зависимости; для проекта с двумя внешними системами это избыточно и замедлит разработку.
- Микросервисы решают проблему масштабирования команд и нагрузок, которых у нас нет; они добавили бы сетевое взаимодействие, оркестрацию и сложный деплой.
- Событийная архитектура оправдана при асинхронных интеграциях и высокой нагрузке; у нас запрос-ответ выполняется синхронно за доли секунды.
- Монолит без слоёв быстрее писать в первые дни, но тесты потребовали бы имитировать Telegram, а логика разрослась бы внутри обработчиков.

## Последствия

**Плюсы**

- Простая и понятная структура, которую легко объяснить на защите.
- Высокая тестируемость бизнес-логики.
- Лёгкая замена слоя хранения.
- Один процесс и один образ — простой деплой и отладка.

**Минусы**

- Слои связаны жёстче, чем в гексагональной архитектуре: сервис напрямую зависит от конкретного класса репозитория, а не от интерфейса. При смене СУБД потребуется вынести интерфейс (например, `Protocol`).
- Масштабирование только вертикальное (или запуск нескольких копий с общей БД); при росте нагрузки архитектуру придётся пересматривать.
- Есть риск «протечки» логики в обработчики, если не соблюдать правила слоёв; это нужно проверять на код-ревью.
- Если появятся фоновые задачи (напоминания, уведомления о лимите), потребуется добавить планировщик или очередь, то есть частично перейти к событийной модели.
