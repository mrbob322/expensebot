# ADR-002: Выбор базы данных

| Поле | Значение |
|---|---|
| Статус | Accepted |
| Дата | 2026-09-30 |
| Автор | Тетюшкин Н.Д. |

## Контекст

ExpenseBot хранит записи о расходах пользователей: идентификатор пользователя, сумму, категорию, комментарий и дату. Основные запросы — добавление записи и суммирование расходов по категориям за период для одного пользователя (см. FR-002, FR-006 в `docs/prd.md`). Данные структурированы, связей между таблицами почти нет.

Ограничения:

- Проект разворачивается на одном недорогом VPS, отдельный сервер БД нежелателен.
- Ожидаемый объём: десятки пользователей, тысячи записей в месяц — единицы мегабайт.
- Финансовые суммы нельзя терять и искажать, нужна транзакционность.
- Автор один, администрировать сложную СУБД некогда.
- В перспективе (PRD, раздел Open Questions) возможен переход на более мощную СУБД.

## Рассмотренные альтернативы

1. **PostgreSQL** — полнофункциональная реляционная СУБД.
2. **MySQL** — популярная реляционная СУБД.
3. **MongoDB** — документоориентированная NoSQL-база.
4. **SQLite** — встраиваемая реляционная база в одном файле.
5. **Redis** — хранилище «ключ-значение» в памяти.

## Решение

**SQLite** на старте проекта. Доступ к данным изолирован в классе-репозитории (`ExpenseRepository`), чтобы в будущем заменить SQLite на PostgreSQL.

## Обоснование

- SQLite не требует отдельного сервера: база — один файл, входит в стандартную библиотеку Python (`sqlite3`), что упрощает установку, тесты (база `:memory:`) и резервное копирование.
- Поддерживает транзакции ACID, поэтому данные не теряются при аварийном завершении процесса.
- SQL удобен для нашей основной задачи — агрегации (`SUM`, `GROUP BY`) по категориям и датам; индекс по `(user_id, spent_on)` ускоряет отчёты.
- PostgreSQL лучше для больших нагрузок и параллельной записи, но требует отдельного сервера, настройки и мониторинга; для MVP это избыточно.
- MySQL по возможностям близок к PostgreSQL, но не даёт преимуществ для нашей задачи, а администрирование сопоставимо.
- MongoDB подходит для слабоструктурированных данных; у нас схема фиксирована, а агрегации проще и надёжнее в SQL.
- Redis хранит данные в памяти и не гарантирует долговременность без дополнительной настройки; как основное хранилище финансовых записей он не подходит. Возможно использование для кэша в будущем.
- Суммы хранятся в копейках (целые числа), а не в `float`, чтобы не накапливать ошибки округления.

## Последствия

**Плюсы**

- Нулевые затраты на администрирование, запуск одной командой.
- Простое тестирование с базой в памяти.
- Надёжное хранение благодаря транзакциям.
- Возможность переезда на PostgreSQL благодаря изоляции в репозитории.

**Минусы**

- SQLite допускает только одну запись одновременно; при сотнях одновременных пользователей возможны блокировки.
- Нет встроенной сетевой репликации; масштабирование на несколько серверов невозможно без миграции.
- Ограниченная типизация столбцов: контроль типов нужно обеспечивать на уровне приложения.
- При переходе на PostgreSQL потребуется миграция данных и проверка совместимости SQL-запросов.
- Файл базы нужно регулярно копировать вручную или скриптом; потеря диска VPS означает потерю данных.
